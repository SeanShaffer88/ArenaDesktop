# ArenaDesktop 0.11.0

A completeness release, and a short one.

v0.10.0 added the command palette — Ctrl+K, type a few letters, Enter. It worked, and it was not finished: the ⋯ menu still held about a dozen things the palette had never learned, so the "one list for every command" was really "one list for most commands, plus a menu you still have to remember".

This release closes that gap and then bolts it shut.

If you are on **v0.10.0**, nothing you already use has moved: no shortcut changed, no menu item disappeared, and every command you knew is where it was.

## What the palette learned

The menu items that had no command now have one:

- **View the log…**, **Open log folder**, **Export a support bundle…** — the three diagnostics chores that used to be two clicks into Help.
- **Connection security…** — the page's address, encryption and the WebView2 runtime, one Enter away.
- **About ArenaDesktop**, **Save as PDF…**, **Open in a new window**.
- **Quick ask** — which focuses the Arena page, ready to type. It was reachable from the tray and `--ask` only, which is an odd place for the app's "put me in the prompt box" gesture to hide.
- **Lock ArenaDesktop**.
- **The five named zoom levels** — 50%, 75%, 100%, 150%, 200%.

Two of those deserve a note.

The zoom levels are generated from the same list the View menu's Zoom submenu draws on, so the two can never disagree. 100% carries **Ctrl+0**, because that key already did it — the old "Reset zoom to 100%" row was deleted rather than left sitting beside a second row for the same thing, and its keywords still include "reset" and "normal" for people who think of it that way.

## Two commands that know when to stay out of the way

The palette now asks the window a question before it lists anything: *does this one apply?*

- **Lock ArenaDesktop** appears once a lock exists. Before that, it is not a command that would fail — it is simply not there.
- **A named zoom level** appears only when the current range can hold it. With the extended range off, 150% and 200% are absent; turn it on and they arrive.

The count under the list follows what is available, so "12 of 49" never implies that eleven commands went missing.

## The part that keeps it honest

A palette that covers the menu will drift the first time somebody adds a menu item, unless something notices. So a test now parses the ⋯ menu in `MainWindow.xaml`, collects every click handler, and refuses to pass unless each one is either mapped to a palette command or listed as an exemption **with a written reason**.

The exemptions are the rows that only make sense in place: the find bar's own Next / Previous / Close buttons, the recovery overlay's buttons, the pinned-mode rows (they depend on what you happen to be browsing), the parameterised mode rows (covered by the nine mode commands), and the items that just open a submenu.

Add a menu item tomorrow and CI tells you to make the same decision the rest of the menu already made.

## The small print, honestly

- **Still no arguments.** The palette runs commands; it cannot take an address, a profile name or a search string. That is unchanged and deliberate.
- **Still no history, still no ranking.** The same query gives the same order, every time.
- **Hidden is not the same as gone.** A command that is not listed is still in the catalogue — if a link or a stale id names one, it is refused rather than run.
- **Pinned mode stays out.** Pinning lives in the status bar and two menu items because it depends on where you are; a palette row for "pin this" would need a palette that knew the current page, which this app deliberately does not.

Everything else is unchanged: three layouts and their cycle, Battle Lab in its side pane, the prompt pad, the field pass, profiles, downloads, the app lock, the updater. Windows runtime behaviour for the new paths — a hidden command, a generated zoom row — remains **Unverified** until the on-machine pass in `RELEASE_CHECKLIST.md` runs; this release adds those checks to it rather than claiming them.
