# Decisions

A living log of significant architecture, UX, security, and dependency decisions.

## 2026-11-03 — Enhancement pack: journal mode + date filters, import strategies, tray favorites, route re-check

- **Journal entries record the mode they ran in — declared by hand, like the winner.** The journal's standing rule is that nothing is read from the Arena page, so the mode is asked in the log dialog (defaulting to the page the prompt was last copied to, correctable before saving) and stored as a canonical registry id on the entry; an unrecognized id sanitizes to "not recorded". Entries logged before this change carry no mode and appear only in an unfiltered view. The window's three filters — prompt name, mode, date range (All time / Last 7 days / Last 30 days, cutoffs computed in Core and inclusive) — shape ONE view shared by the list, the scoreboard and the Markdown export, extending the v0.3.0 rule that the tally always describes what is on screen.
- **Import gains clash strategies; "merges, never replaces" becomes the default instead of the only behavior.** The 2026-11-02 import decision held that an import can never silently overwrite an existing prompt. That protection now stands as the DEFAULT (Skip), and the user may choose per import — one choice, asked once, applied to the whole file — to Replace (the incoming category and body take over; the existing prompt keeps its id, so queue entries naming it survive) or Keep both (the incoming prompt lands under Duplicate's "… copy" naming, via the shared CopyNameFor helper). A prompt whose title AND text both match is the same prompt, not a clash, and is skipped under every strategy. `MaxPrompts` binds everything that grows the library (fresh titles, keep-both) and never binds Replace. The parameterless `ImportPrompts` keeps the exact v0.3.0 merge semantics for any other caller.
- **Favorites get their own tray submenu.** Favorites already lead the Arena modes submenu (starred, v0.3.0); a separate Favorite modes submenu beside it lists ONLY the favorites in the user's order — or a single disabled "No favorites yet" item, so the menu shape is stable and the feature discoverable. Each click dispatches through the same `NavigateArenaMode` path as the modes submenu, the window's mode jumps, the keyboard shortcuts and arenadesktop:// links. It rebuilds on every menu open, like the modes submenu, so a Settings change shows without a restart.
- **The Diagnostics route check re-runs while the window is open.** A two-minute DispatcherTimer (the tray's blocked-suspend recheck cadence; the probe is nine small parallel HEAD requests, so the traffic is negligible) re-runs MainWindow's unchanged reachability probe, a tick landing mid-check is skipped rather than queued, and the window stamps "Last checked HH:mm" beside the button so a stale verdict can't pass as fresh. Manual-first: nothing runs at open — the button covers "now" — and closing the window stops the timer.
- **Run-queue reorder needed no work.** The request to add queue reorder and single-remove restated an existing capability: Core's `MoveInQueue` / `RemoveFromQueueAt`, the window's ↑ / ↓ / Remove buttons, and Core tests all shipped with the queue. Verified against the tree; nothing rebuilt.

## 2026-11-02 — Seamless updates: the installer closes and reopens the app (MuseDesktop R7D/R7D1 design, ported)

- **The direction: upgrading is hands-free after the user accepts it.** The accept step is untouched — the update window's Download → verify → Install, or the user running the installer themselves. Everything after that one decision needs no further interaction: no wizard in the in-app path, no "please close the app first", no manual relaunch. ArenaDesktop's installer used to do none of this; this entry ports the design MuseDesktop shipped as R7D (v1.8.4) and rebuilt as R7D1 (v1.8.5) after a field failure, with names adapted (ArenaDesktop.exe, arenadesktop://, Arena registry keys) and no Muse branding carried over.
- **The handshake, end to end.** The in-app Install now launches the verified installer with `/S` and does NOT exit the app itself (the old flow launched the wizard, then exited — replaced, because the installer's relaunch decision comes from detecting the RUNNING instance at install start). At the top of its main section — before any file is copied — the installer checks whether ArenaDesktop is running; if it is, it runs the INSTALLED `ArenaDesktop.exe --exit-for-update`. That second process reduces the flag to a new intent (Core: `LaunchIntentKind.ExitForUpdate`), writes it to the pending-intent file, knocks the wake event, and exits; the running instance applies it through the ordinary exit path (`ExitApp` — state saved, tray disposed). The installer then polls for the process to disappear (≈15 s), falls back to asking every ArenaDesktop process to close its main window (PowerShell `CloseMainWindow`, ≈10 s), then to `taskkill /F` (≈5 s), and proceeds with the install regardless.
- **Detection is process-based from day one — the mutex design is deliberately NOT ported.** MuseDesktop's first version detected the running app by opening its single-instance mutex (System plugin, OpenMutexW) and that check never once fired in the field: the close was silently never attempted. Its replacement asks PowerShell `Get-Process ArenaDesktop` and reads the answer from the exit code (0 = running, anything else = not running): no object names to match, no handles, no plugin call shapes. Every step of the close chain prints a `DetailPrint` line, so a future field failure leaves its story in the install details view instead of silence.
- **The exit intent is the ONE intent that never waits behind the app lock.** Core's routing (`LaunchIntentRouting.AppliesImmediately`) applies it at once, locked or not: exiting reveals nothing, navigates nowhere, and names no profile, and the lock re-engages at the next launch as after any exit. Every other intent keeps the S11 rule. It also never shows the window: the wake handler feeds `ApplyLaunchIntent` directly, so a tray-hidden instance exits without ever appearing. And a `--exit-for-update` launch that finds NO running instance exits quietly itself instead of starting the app the installer is about to replace.
- **Relaunch belongs to the finish page; silent mode is the one exception, and its reason is consent.** Interactively, the ONLY relaunch is the finish page's "Run ArenaDesktop" checkbox, which MUI fires as the wizard closes — the app starts as the installer goes away, and only when the box is ticked. When the app was running at install start, `AdFinishPageShow` pre-ticks the box (the app was open — bring it back); the user's untick always wins; when nothing was running, the box keeps its stock state. A `/S` run has no finish page and no checkbox, so a hidden last section relaunches the app when it was running AND the run is silent: in-app installs are that silent path, and the click on Install inside the app IS the consent.
- **The uninstaller runs the close chain too — a deliberate difference from MuseDesktop's script.** MuseDesktop's uninstaller does not close the app (its file removal simply leaves anything locked in place). ArenaDesktop's uninstaller runs the same chain first (DetailPrint prefix "Uninstall"): a running instance would otherwise lock the program folder, and — when the user answers Yes to deleting data — the WebView2 profile folders the app holds open. The chain is one shared macro (`AD_CLOSE_RUNNING`), so install and uninstall can never drift into different close behavior.
- **Deliberately not ported.** MuseDesktop's saved-password wipe (its R7F) is a Muse-specific repair for passwords its pre-v1.8.8 builds let the web view save, driven by an owner rule about that app; it is not update machinery and ArenaDesktop has no equivalent legacy state to repair. The rollback path (`ReinstallPreviousVersion`) is also untouched, exactly as in MuseDesktop: kept installers predate this feature, their handshake cannot be assumed, so rollback keeps its confirm → wizard → exit flow with no silent flag and no auto-relaunch.
- **Old builds facing the new installer.** A pre-port build tolerates the unknown flag (arguments are never fatal) and merely wakes its window, so the handshake politely does nothing and the fallbacks do the close — still automatic, still relaunched, just less gentle. Updating FROM v0.3.0 or older therefore works; the fully gentle path needs both sides at this version or later.
- **Windows runtime: Unverified**, like the rest of the app, until the on-machine pass runs: the process check's timing on a real machine, the pre-ticked box, the silent relaunch, and the uninstall close are all field checks now listed in RELEASE_CHECKLIST.md.

## 2026-11-02 — Modes pack (v0.3.0): route health, startup mode, favorite modes

- **Route health is reachability-only, by design.** Diagnostics' "Check mode routes" asks each registered mode route's server to answer (HEAD, GET only where HEAD is refused with 405) and classifies the outcome in Core (`RouteHealth`): 2xx/3xx and 401/403 mean the route exists, 404 means Arena moved it (the one verdict that asks for a registry update), everything else — network error, timeout, 5xx — is Unreachable. Response bodies are discarded unread (headers-only reads): the check never looks at page content, keeping the standing no-page-reading rule. The log records host + path and the verdict class only. Classification and formatting are Core-tested; the HTTP calls are the shell's.
- **The startup mode composes with the start page; it does not replace it.** The per-profile start page (S5 #47 — restore last page / Home / custom URL) names a PAGE and still wins wherever it does so. The new app-wide `StartupMode` string ("battle" default, "last", or "mode:<id>", resolved by `StartupModes.ResolveStartupMode`, unsalvageable values sanitize to "battle") only picks which mode page stands in for Battle when a launch would land on the Arena home page anyway — no crash restore, no custom fallback, never in safe mode. Default = Battle = exactly today's behavior.
- **Last-used mode is stored per profile.** `LastModeIdByProfile` sits next to `LastUrlByProfile` and follows its reasoning: Arena sessions are account-scoped, so one profile's last mode is never another's startup suggestion. It is session state, not a preference — reset-all-settings preserves it, while `StartupMode` and `FavoriteModeIds` reset with the other preferences.
- **Favorites are a short ordered list, sanitized like everything else.** At most three ids (`FavoriteModes`), unknown ids and duplicates dropped on load. They lead the tray's Arena modes submenu (starred, one separator) and the Jump List's modes category — where Battle and Leaderboard, the pair the list has always carried, still follow when they aren't favorites themselves. No favorites = both surfaces keep their exact previous order.
## 2026-11-02 — Battle Lab pack (v0.3.0): copy targets, library transfer, queue and journal tools

- **Copy targets are the three text modes, through the same callback.** The copy button's picker offers Battle, Direct Chat, and Side by Side (the modes with a prompt box worth pasting into). The Battle Lab → main window callback now carries the mode id (`Action<string>`), and the main window resolves it through `ArenaModes.TryGet` with Battle as the fallback — the same registry dispatch as every other surface, and Battle remains the default when nothing is picked. The copy itself is unchanged: fill blanks, clipboard, user pastes; nothing is injected.
- **The library export format carries a marker and a version.** Exports are `{ "format": "arenadesktop-battle-lab", "version": 1, "prompts": [...] }` with only the prompts inside — the queue and journal are this PC's run state and do not travel. A file whose marker or version doesn't match, or that won't parse, imports nothing and is reported as "not a Battle Lab library file", so a settings export or random JSON can never half-merge.
- **Import merges; it never replaces, and ids are always fresh.** An incoming prompt is skipped when one with the same name (case-insensitive) and the same body is already in the library; everything else is added under a NEW id minted by the library (the file's ids are not even reused as slugs), so an import can never collide with or silently overwrite an existing prompt.
- **One cap for merge operations.** The library cap (`BattleLabLibrary.MaxPrompts`, 200) is enforced by Duplicate and Import — the two operations that can grow the library in bulk or by accident — which stop at the cap and say so, rather than trimming anything already there.
- **The scoreboard tallies what is on screen.** The journal's tally is computed over the currently filtered entries, in Core (`BattleJournalTally`), and the Markdown journal export renders exactly that filtered set with its tally — filter first, and both the line and the file describe the same battles.

## 2026-11-02 — Field pass (v0.2.0): guided checks, user-recorded verdicts

- **Its own modeless window.** The field pass opens from the ⋯ menu, from Diagnostics (which closes first — Diagnostics is modal, the pass is not), `--field-pass`, and `arenadesktop://field-pass`, routed through the same LaunchIntent registry as every other capability. Modeless matters: a check's "Open feature" button opens Settings / Battle Lab / Downloads while the pass stays open.
- **The app verifies nothing.** Every check is a shell check the user performs by hand and marks Pass / Problem / Skip; the app never injects into or reads from the Arena page to "help". The pass's value is structure and memory — exact steps, what working looks like, and a durable record — not automation theatre.
- **One JSON store, Core-owned.** `FieldPassSession` / `FieldPassStore` in `ArenaDesktop.Core` hold the catalogue, verdicts, counts, and the summary renderer (`field-pass.json` in the app data folder), following the repo's store patterns: atomic replace, a corrupt file preserved as a `.corrupt-…` copy with a fresh pass loaded, autosave on every verdict and note, and no seed content — a fresh pass is simply unmarked.
- **A help page rides along.** The catalog gained a field-pass page whose action opens the pass (Help closes first, for the same modal reason as Diagnostics), keeping `Help.md` and the Core catalog in lockstep as the drift guard requires.

## 2026-11-02 — Battle Lab (v0.2.0): prompt library, run queue, results journal

- **Its own window, not a panel.** Battle Lab is a modeless window opened from the ⋯ menu, the tray, `--battle-lab`, and `arenadesktop://battle-lab` (routed through the same LaunchIntent registry as every other capability). Modeless matters: copying a prompt brings the main window forward on Battle while the Lab stays open for the next run and for logging the result.
- **Copy, never inject.** "Copy prompt & open Battle" fills the prompt's [blank] placeholders in a small dialog, puts the finished text on the clipboard, and navigates the main window to Battle through the ArenaModes registry. The user pastes. This keeps the standing rule intact: the app never injects script into arena.ai and never reads anything back from the page.
- **The journal is manual by design.** Results (A won / B won / Tie + note) are recorded by the user; nothing is scraped or detected. Journal entries snapshot the prompt name, so deleting a prompt never rewrites history.
- **One JSON store, Core-owned.** `BattleLabLibrary` / `BattleLabStore` in `ArenaDesktop.Core` hold all logic and persistence (`battle-lab.json` in the app data folder), following the repo's store patterns: atomic replace, a corrupt file preserved as a `.corrupt-…` copy with an empty library loaded, autosave on every change, and four editable seed prompts written only on first run (deleting them all is permanent — no re-seeding).
- **Queue completion is automatic but honest.** "Use next from queue" starts the head prompt; when a result is logged for that prompt while it is still at the head, it leaves the queue. Explicit Remove and Clear are always available, and nothing else is removed implicitly.

## 2026-10-27 — ArenaDesktop v0.1.0: a MuseDesktop-parity fork for arena.ai

- **Fork, don't reinvent.** ArenaDesktop starts from the MuseDesktop codebase (same author's MIT project) at its v1.0.0-era tree, renamed throughout. Reason: the parity target — tray, downloads manager, profiles, app lock, recovery, in-app updates with hash verification — is already built and covered there by a large Core test suite. A clean room rewrite would re-learn the same WebView2 lessons at full cost. The fork keeps the Core/shell split: all testable logic in `ArenaDesktop.Core` (plain .NET 10, no Windows APIs), the WPF app as a thin shell.
- **Stack deviation inherited: C# / WPF + Microsoft's WebView2 SDK instead of Rust.** The documented MuseDesktop reason stands: the first-party SDK is what exposes the exact features this shell needs (persistent user-data folder, new-window/navigation events, permission requests, download operations with progress + ETA). WebView2 SDK stays pinned at 1.0.4258.31; bumps are deliberate, with release notes checked.
- **Version restarts at 0.1.0.** ArenaDesktop is a new product; carrying MuseDesktop's version history would lie about its maturity. Its Windows runtime is Unverified until the release checklist runs on a real machine.
- **URL policy for Arena.** Home is `https://arena.ai/`. New-window in-app hosts: `arena.ai`, `lmarena.ai` (Arena's previous domain, still linked from older content), and the sign-in providers Arena uses — `accounts.google.com`, `appleid.apple.com`, `login.microsoftonline.com`. Microphone and notification permissions auto-grant only to `https://arena.ai` origins; everything else is denied rather than silently granted. Full URLs are never logged (host + path only).
- **Arena modes are one registry.** `ArenaModes` in Core defines Battle, Direct Chat, Side by Side, Leaderboard, Agent, Image, Code, Video, and Web Search once; the window menu, the tray, the Jump List, Ctrl+1…Ctrl+9, the CLI flags, and `arenadesktop://` links all dispatch through it. Addresses verified against the live site on 2026-10-27: Battle is the home page; Direct Chat is `/text/direct` and Side by Side is `/text/side-by-side` (models picked at the top of those pages); Leaderboard is `/leaderboard`; Agent, Image, Code, Video, and Web Search are top-level pages. The app never injects script into arena.ai.
- **Global hotkey is Ctrl+Alt+A**, not MuseDesktop's Ctrl+Alt+M, so both apps can run side by side without fighting over the key. Registration id changed to match.
- **No winget.** The maintainer has no code-signing certificate; distribution is GitHub Releases only and binaries ship unsigned, stated honestly. The winget packaging folder from the fork base was removed.
- **Release shape.** x64 and ARM64 at v0.1.0 (the architectures the fork base's CI builds and verifies), with the fork base's asset naming, which the in-app updater pins in code and tests: `ArenaDesktop-Setup-v<version>-<arch>.exe`, `ArenaDesktop-v<version>-windows-<arch>.zip`, plus `SHA256SUMS.txt` — the sums file is a working part of the updater (it refuses a release without one), not decoration. x86 and MSI are not shipped in this version and are named as gaps in the release notes, not silently skipped.
- **Icons/assets.** The fork base's icon artwork is reused for v0.1.0 (renamed); a distinct ArenaDesktop icon is a capture/design task, not a blocker.

## 2026-11-02 — Shell layouts ported from MuseDesktop 2.0.0

- **Three layouts, one Core model.** `ShellLayout` / `ShellLayoutMetrics` / `ShellLayoutCycle` in ArenaDesktop.Core mirror the parity target's design: Standard is exactly ArenaDesktop's long-standing chrome (40px toolbar, 24px status bar); Compact Focus pins a 30px toolbar and trades the status bar for a floating status pill (the page gains 34px of height); Left Rail pins the same 30px strip, keeps the status bar, and takes a 56px rail (gain 10px). ArenaDesktop has no chrome-density setting, so the metrics resolve without the target's density input — the one deliberate adaptation.
- **The default changed; saved choices did not.** New installs (no saved layout) start in Compact Focus. A persisted layout always wins, and `Sanitized()` repairs an undefined value to Compact Focus — the same semantics as the parity target, so an upgrade never rearranges an existing user's window. A settings reset returns the layout to Compact Focus with the other appearance preferences.
- **The rail is Arena's navigation, not the target's.** The target's rail carries that app's own destinations; ArenaDesktop's carries Back / Forward / Reload / Home, the nine Arena modes (the same `ArenaModes` dispatch as Ctrl+1…Ctrl+9, the ⋯ menu, the tray and the Jump List), Downloads, and profile switching, with Settings and the ⋯ menu at the foot. The mode column scrolls when the window is too short to show all of it. In Left Rail the top strip keeps only the title/address and the zoom cluster; the pin and Open-in-browser stay one ⋯-menu click away.
- **Switching surfaces.** Settings → Appearance & toolbar (a Shell layout picker) and the ⋯ menu's three checkable layout items. There is no cycle shortcut: ArenaDesktop has no command palette, which is where the target's cycle entry lives.
- **Windows runtime: Unverified**, like the rest of the app, until the on-machine pass runs.
