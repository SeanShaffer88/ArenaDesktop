## 2026-11-23 — Multi-view tabs: one environment, a view per tab, a hard cap

- **Every tab view shares the profile's single `CoreWebView2Environment`.** One environment per tab would mean one user-data folder — and one sign-in — per tab, which defeats profiles. All views (and the hidden retry view) are created from the one environment over the profile folder, so sign-in is shared across tabs exactly as it already was across windows.
- **`Browser` remains the name of the active view.** MainWindow referenced the single control from ~100 places, nearly all of them meaning "the page the user is looking at" (find, zoom, print, mode jumps, palette and CLI navigation). Rather than churn every call site, the field is repointed on tab switch and the incoming control is swapped into the focus ring. Per-view event handlers resolve their owning view from the sender: durable tab state updates for every view, chrome effects only for the active one. All views are wired through the one `WireView` path, so settings and policy handlers are identical per tab by construction.
- **Six live views, LRU eviction, no background suspension.** A live view is a full renderer; `TabSet.MaxLiveViews` (6 of 12 tabs) bounds memory, with Core owning the eviction decision (least-recently-activated background tab; the active view is never evicted) and the shell only disposing/creating controls. Background views are deliberately NOT suspended on switch — there is no reliable "this page is streaming" signal, and freezing a background Agent task is worse than its memory cost. Tray hide is the one suspension path, and there WebView2 itself declines for active media per view.
- **A browser-process crash costs background tabs their in-page state.** The shared environment dies with the process, so recovery recreates the active tab's view at its last page and leaves background tabs uncreated; they rebuild at their persisted URLs on next activation. Per-renderer failures reload only the failing view.
- **Live-view bookkeeping is runtime-only.** `TabSet.LiveViewIds` is `[JsonIgnore]` — a view exists only while the process runs, so persisting the list would resurrect a lie after every restart. Settings `SchemaVersion` stays 1; nothing about the persisted tab shape changed.
- **Windows runtime: Unverified** — the multi-view shell is built and Core-tested on the maintainer's VM; no on-machine pass has run.

## 2026-11-23 — Completeness program: portable profiles move, DPAPI honesty stays (slice A)

- **Portable mode now relocates the WebView2 profiles** under the portable data root (`SettingsLocation.WebViewProfileDir` is the pure resolver; `AppPaths.ProfileDir`/`WebViewDataDir` are the single choke point every consumer already used). Installed mode paths are byte-identical to before. No migration either way — the standing portable rule.
- **We do not claim cross-machine sign-in portability.** WebView2 cookies are DPAPI-bound to the creating Windows user+machine; a copied profile folder cannot decrypt elsewhere. The plan's original "encrypted session export" idea is not implementable honestly, so slice A delivers same-machine portability and section E's encrypted backup covers settings + profile metadata only. Every user-facing description says this plainly.

## 2026-11-23 — Completeness program: native developer tools, and two deliberate refusals (slice C)

- **No file-system bridge into Arena's web agent — decided, not deferred.** Giving the web agent access to local files would require script injection, a host object, or a WebMessageReceived bridge into arena.ai pages; SECURITY.md forbids all three, and Arena offers no sanctioned local-files protocol. The desktop value is therefore native and beside the agent: Git panel, terminal, and task notifications over a user-chosen project folder.
- **Connector OAuth stays in the web view.** Managing Arena connector credentials natively would mean the app handling Arena account tokens outside Arena's own flow. Not built; what is native is notification of long-running local tasks (terminal/git/downloads/comparisons).
- **Git runs non-interactively** (`GIT_TERMINAL_PROMPT=0`, the user's own credential helper): a missing credential fails plainly instead of hanging a hidden process forever. Pull is `--ff-only` so the panel never creates a surprise merge commit.

## 2026-11-23 — Completeness program: BYOK keys live in a DPAPI vault, never in settings (slices B1/B2)

- **Keys are not settings.** `ApiKeyVault` stores each key as a protected blob in `api-keys.json`; settings.json carries provider configs only, so the existing settings export/import can never leak a key. The shell protector is DPAPI current-user via crypt32 P/Invoke (no new package); Core's `ISecretProtector` seam keeps the vault testable and a passphrase protector (PBKDF2 + AES-GCM) ships in Core for tests and any future non-Windows host.
- **Each provider keeps its real API shape.** Anthropic is not squeezed through an OpenAI-shaped shim: its system split, `x-api-key`/`anthropic-version` headers and event-stream deltas are modelled as-is, as are Google's `contents[]`/`:generateContent` shape. Ollama and LM Studio ride the OpenAI-compatible path at their localhost defaults.
- **No live network in tests** — `ChatClient` takes an injected `HttpMessageHandler`; the suite uses a fake.

## 2026-11-23 — Simple Mode is a Core policy, and the fuzz corpus is seeded (audit pass, unreleased)

- **One policy, every door.** Simple Mode's decisions live in Core (`SimpleModePolicy`): whether Battle Lab, the prompt pad and the command palette are available, which palette commands survive the filter, and which tray entries stay visible (Open and Exit only). The shell only hides and refuses. That matters because each surface has at least five doors (⋯ menu, tray, keyboard, command line, `arenadesktop://` link) and a shell-only implementation would have had to remember all of them in several places; here the open-methods refuse centrally and the menus/tray consult the same rule.
- **Hidden means unreachable, not greyed out.** The items leave the menus, the shortcuts route through the same guarded open-methods so they refuse too, the palette cannot open at all, and turning Simple Mode on closes a Lab pane or pad window that is already open. Nothing is deleted: the library, queue and pad draft are exactly where they were when the mode is turned back off.
- **The fuzz harness adds no dependency.** `UriFuzzingTests` generates its corpus from a seeded `Random` plus mutations of valid links. FsCheck/SharpFuzz would give smarter generation, but the invariants being defended (never throw; accepted ⇒ allowlisted) do not need it, a seeded corpus reproduces a failure exactly, and the test project stays at its current dependency set.
- **PERFORMANCE.md records no invented numbers.** The brief asked for measured baselines; measurements require a Windows machine and the first field pass has not run. The file therefore carries the methodology and an explicitly empty baseline table rather than figures produced on a Linux VM, which would be fiction. The project rule stands: budgets are declared at the first field pass, measured, not guessed.
- **Windows runtime: Unverified** for Simple Mode's shell gating until the on-machine pass covers it.

## 2026-11-23 — The palette's fifth verb is `saved`, not `prompt` (v0.14.0)

A verb that takes an argument also takes words away from the search. "prompt
pad" is a documented way to reach the pad (Help.md lists it beside `settings`
and `downloads`), and a `prompt <text>` verb would have turned that pair into a
question about a saved prompt called "pad" — a regression dressed as a feature.

So the verb is **`saved`**: `saved cables` copies that Battle Lab prompt. No
command title starts with the word, "saved" alone is still a search, and a test
pins the pair that forced the choice (`prompt pad` parses as a search and still
finds `prompt-pad`).

Two rules came with it. **Ranking is stated**: exact name → name prefix → name
contains → category → body, first rank that finds anything wins. A search that
silently prefers one prompt over another is how you copy the wrong thing.
**A tie is a shortlist**: several matches open Battle Lab filtered to them and
say how many, rather than one being chosen for you. It is the same refusal the
queue command makes about blanks — the app does the mechanical part and leaves
the judgement to the person.

# Decisions

A living log of significant architecture, UX, security, and dependency decisions.

## 2026-11-23 — Prompt pad (v0.9.0): a scratchpad beside the library

- **A third prompt surface, and the smallest.** Battle Lab is a library (kept, categorised, journaled) and Quick ask is a jump that focuses Arena's page. Neither is the right shape for a prompt you are about to try exactly once: the Lab makes you file it first, and Quick ask has nowhere to write it. The prompt pad is one box, one page picker and a copy button, opened with Ctrl+Shift+P, ⋯ → **Tools** → *Prompt pad…*, the tray menu, `--prompt-pad` or `arenadesktop://prompt-pad`, all dispatched through the same LaunchIntent registry as every other capability.
- **Copy, never inject — unchanged.** The pad puts text on the clipboard and navigates the main window to the mode the user picked, then puts the keyboard in the page. It never types into arena.ai and never reads the page: the same rule Battle Lab's copy button and Quick ask have always followed. "Copy & open <page>" is worded so it does not claim the paste happened, because it hasn't.
- **One pad, modeless, single-instance.** Like the field pass it is modeless so the page stays usable while it is open, and like every other surface there is exactly one: a second request activates the open window instead of stacking a second pad on the same file.
- **Locked means hidden, not closed.** The pad is a window of its own and can hold a prompt, so the app lock hides it on the way in rather than leaving it on screen behind the lock screen — and rather than closing it and throwing the text away. Unlocking brings the box back exactly as it was, with the main window in front. The tray item is disabled while locked, like the other content surfaces.
- **Its own small file, not settings.json.** `prompt-pad.json` holds the last ten prompts and the last page chosen. Prompts in settings.json would bloat the settings export and the support bundle's sanitized settings; a separate store follows the repo's atomic-write and corrupt-preserved patterns and travels in portable mode. Ten entries is deliberate — the pad is not a library, and Battle Lab already is.
- **The clipboard-lifetime timer lives in the main window.** With "Clear copied prompts from the clipboard after…" on, Battle Lab's pane keeps its own timer, but the pad closes the instant it copies, so a timer inside it would die with the window and the setting would quietly stop applying to pad copies. The main window arms the same Core rules (`ClipboardLifetime`) on the pad's behalf: it never clears while the app is locked, and it only ever clears text this app put there.
- **Listed like everything else, in the same change.** Shortcut catalog (fixed Ctrl+Shift+P, so the shortcut sheet lists it), the ⋯ menu's Tools group, the tray menu, the command line, an `arenadesktop://` route and a Help page all land together — that is what keeps the surfaces from drifting, and the Core tests pin each of them.
- **The long-prompt rule is Battle Lab's, minus the export.** The pad reuses `PastedTextPolicy` (6,000 characters, the exact size in the warning) but offers only copy-anyway, not export-as-.txt: exporting is Battle Lab's affordance, and a second save dialog in a scratchpad would be friction, not safety. The limitation is recorded in KNOWN_LIMITATIONS.md.

## 2026-11-11 — ARM64 support dropped (v0.7.0)

- **What changed.** `v0.7.0` ships x64 only. The ARM64 CI job, the ARM64 release assets and the ARM64 download links are gone; a release now carries three assets instead of five.
- **Why.** ARM64 was carried because the fork base's CI built it, not because anyone asked for it. It doubles the build matrix, the installer count, the download surface and the on-machine pass — and the on-machine pass has never actually run on an ARM64 machine, so the ARM64 build was **shipped but never verified**. Keeping an unverified native build on offer is worse than not offering it.
- **What was NOT changed: the architecture logic in the updater.** `UpdateAssets.ArchToken` still names whatever architecture is running, and `PickInstaller` still matches on it. An arm64 install of 0.6.0 (or of any earlier release) therefore keeps working: it names `arm64`, finds no `-arm64.exe` in the newer release, and is offered nothing. That is the correct outcome — a wrong-architecture installer is never offered, and the check is already covered by `S9Tests`. Hard-coding "only x64 exists" would have broken the one case that matters.
- **Consequence for ARM64 users on 0.6.0 and earlier:** they stay on their current version. There is no update path, and the in-app update check says so plainly rather than failing mysteriously. `KNOWN_LIMITATIONS.md` names this. A Windows-on-ARM PC can still run the x64 installer under emulation, and that is stated rather than implied.
- **Also fixed while here:** `sign-release.yml` regenerated `SHA256SUMS.txt` with `Set-Content -Encoding ascii`, which writes a BOM and CRLF. `SumsFile.Parse` takes the first 64 bytes of each line as the hash, so a BOM'd file is unreadable to the updater — the same trap already fixed in `release.yml`. It now writes LF, ASCII, no BOM.

## 2026-11-11 — Releases are built by a workflow, not by hand

- **The problem was reproducibility, not convenience.** Releases were built on one machine: `dotnet publish` per architecture, `makensis` per installer, sums written by hand. That left the project unable to ship whenever that machine was unavailable, and it meant every release depended on a human repeating eleven steps correctly. The steps were already documented in RELEASE_CHECKLIST.md — the pipeline is those steps, written out.
- **Triggered by a tag, verified against the code.** `push: tags: v*` is the whole interface. The gate runs before anything is built: the tag must be `v<major>.<minor>.<patch>[-suffix]`, must equal `<Version>` in the csproj, and `WhatsNew.md` must carry that version's section. The version is the tag's, never derived from the branch — a tag is the only thing here that cannot drift.
- **A hand-written notes file wins over the changelog section.** `docs/release-notes/vx.y.z.md` is optional; when present it is used verbatim, otherwise the version's CHANGELOG section is. This exists because a release sometimes has to say more than its own changes: 0.4.0 and 0.5.0 were developed and never published, so 0.6.0 is the first release since 0.3.1 and its notes carry all three. Resolution order is file, then changelog — the pipeline never edits either.
- **The installer and the zip ship the same bytes.** Both are built from one `dotnet publish` folder per architecture, so the two channels cannot diverge. The zip gains the four docs `ci.yml` already stages; the installer packages that identical folder.
- **It will not overwrite a published release.** A re-run for an existing tag fails rather than clobbering. Recovering means deleting the release or bumping the version — deliberately a human decision.
- **It re-downloads what it published and re-verifies it.** The final step fetches all three assets back from the release and checks every hash against `SHA256SUMS.txt`. That is RELEASE_CHECKLIST's "a release is not shipped until its assets are hash-verified", moved from a manual step onto the critical path.
- **What it does not do:** it does not sign (see the `sign-release.yml` enable path and the signing section below), and it does not replace the on-machine pass — the checklist's Windows 10/11 walkthrough still has to happen on real hardware before a build is called Verified.

## 2026-11-11 — Enhancement pack (twenty improvements)

- **Everything new lives in Core first.** Each item is a small pure model with tests (`Enhancements.cs`, `Enhancements2.cs`, `Enhancements3.cs`): find-option policy and find-bar keys, zoom presets, session stats and the reading-time clock's rules, the error-code lookup, the shortcut cheat sheet's grouping/search, the long-prompt policy, download sort bands, the folder check, the startup trend, duplicate detection, the pinned mode, startup restoration, and the run-queue move. The shell only draws them, so each rule is pinned by tests rather than discovered in a handler.
- **Find options are WebView2's own flags, not a second finder.** The bar's *Whole word* and *Match case* map to `CoreWebView2FindOptions.ShouldMatchWord` / `IsCaseSensitive` — checked against Microsoft's reference for the pinned SDK 1.0.4258.31 before wiring. There is no regular-expression option in that API, so the pack does not pretend to offer one (an earlier draft hand-rolled a regex flag and was removed); the app still never looks at page content itself, and a changed option re-runs the find so the count can never describe the old rules.
- **The session numbers are deliberately ephemeral.** Session stats live in memory for the life of the process and are never written to `settings.json`, the log, or anywhere else; the window and the Diagnostics block both say so. Reading time only accrues while the window is visible, ignores deltas over four hours (so a sleep or a clock jump can't inflate it), and caps each visit — an over-claiming "time on Arena" would be worse than no number at all.
- **The pinned mode is a preference that offers a jump, not a navigation rule.** It is stored as a validated registry id (`PinnedMode.Sanitize`, unknown ids read as nothing pinned), survives restarts, resets with the rest of the preferences, and never changes what a launch opens — the status-bar label and the ⋯ items are the entire feature. The status-left/right split means download detail outranks the pinned label while a transfer runs.
- **Startup restoration got a narrower guard, not a new policy.** `StartupRestore.IsUsableLastPage` only answers "is this remembered address still an https Arena page?"; `StartPagePolicy` and safe mode keep their exact existing precedence, and an unusable remembered page logs redacted and falls back to the resolved start page instead of showing a failure screen.
- **Downloads stay one query, extended in place.** `DownloadsView.Apply` composes search, state, the new size band and the five sorts in one Core function; the older `DownloadHistoryQuery` is untouched for its callers. Size bands are named presets (never a typed number) and the max is exclusive, so the bands can't overlap. The history summary total describes exactly the filtered view.
- **The folder check reports what it measured.** Settings probes existence, writability (a tiny probe file, created and deleted) and free space; anything it couldn't measure is named as unmeasured in the line — a folder that can't be probed is never shown as healthy.
- **Honest diagnostics additions.** The startup trend uses medians of the last three runs against earlier runs and needs at least four recorded runs before it says anything; the session block repeats that it is this-run-only. Both are optional on `DiagnosticsData`, so callers that don't collect them keep the report's previous shape (pinned by a test).
- **Duplicate detection separates identity from access.** Same-text groups ignore case and whitespace runs (a real duplicate); same-name groups list distinct categories, because two prompts may legitimately share a name across categories. Empty bodies are never duplicates of each other.
- **The long-prompt warning is a warning, not a limit.** The app cannot know Arena's prompt-box limit — it is the page's own field — so it warns above 6,000 characters, shows the exact size and a preview, and offers copy-anyway or an export to a .txt file. Short prompts take the old path with no extra click.
- **Dimming is shell-only and opt-in.** `ShellQuiet` lowers the toolbar's opacity only while the Arena page holds focus and the setting is on, never below 0.72 (the buttons must stay discoverable), and restores on hover or a focus change. The page is never restyled, and the default is off so the existing look is unchanged.
- **Windows runtime: Unverified**, like the rest of the app, until the on-machine pass runs: the find-option round trip, the pinned label's click target, the reading clock across a tray hide, and the folder probe on a real drive are all field checks.

## 2026-11-05 — Downloads refresh on tracker notifications

The Downloads window coalesces tracker progress on the WPF dispatcher. Completion and failure refresh persisted history after the tracker records the outcome. Opening the window still loads history, and local delete and clear actions refresh it directly. The window unsubscribes when closed. A timer updates the countdown only while a visible in-progress row has a future ETA. Its tick reads the in-memory tracker, and idle windows perform no recurring history reads.

## 2026-11-03 — Enhancement pack: journal mode + date filters, import strategies, tray favorites, route re-check

- **Journal entries record the mode they ran in — declared by hand, like the winner.** The journal's standing rule is that nothing is read from the Arena page, so the mode is asked in the log dialog (defaulting to the page the prompt was last copied to, correctable before saving) and stored as a canonical registry id on the entry; an unrecognized id sanitizes to "not recorded". Entries logged before this change carry no mode and appear only in an unfiltered view. The window's three filters — prompt name, mode, date range (All time / Last 7 days / Last 30 days, cutoffs computed in Core and inclusive) — shape ONE view shared by the list, the scoreboard and the Markdown export, extending the v0.3.0 rule that the tally always describes what is on screen.
- **Import gains clash strategies; "merges, never replaces" becomes the default instead of the only behavior.** The 2026-11-02 import decision held that an import can never silently overwrite an existing prompt. That protection now stands as the DEFAULT (Skip), and the user may choose per import — one choice, asked once, applied to the whole file — to Replace (the incoming category and body take over; the existing prompt keeps its id, so queue entries naming it survive) or Keep both (the incoming prompt lands under Duplicate's "… copy" naming, via the shared CopyNameFor helper). A prompt whose title AND text both match is the same prompt, not a clash, and is skipped under every strategy. `MaxPrompts` binds everything that grows the library (fresh titles, keep-both) and never binds Replace. The parameterless `ImportPrompts` keeps the exact v0.3.0 merge semantics for any other caller.
- **Favorites get their own tray submenu.** Favorites already lead the Arena modes submenu (starred, v0.3.0); a separate Favorite modes submenu beside it lists ONLY the favorites in the user's order — or a single disabled "No favorites yet" item, so the menu shape is stable and the feature discoverable. Each click dispatches through the same `NavigateArenaMode` path as the modes submenu, the window's mode jumps, the keyboard shortcuts and arenadesktop:// links. It rebuilds on every menu open, like the modes submenu, so a Settings change shows without a restart.
- **The Diagnostics route check re-runs while the window is open.** A two-minute DispatcherTimer (the tray's blocked-suspend recheck cadence; the probe is nine small parallel HEAD requests, so the traffic is negligible) re-runs MainWindow's unchanged reachability probe, a tick landing mid-check is skipped rather than queued, and the window stamps "Last checked HH:mm" beside the button so a stale verdict can't pass as fresh. Manual-first: nothing runs at open — the button covers "now" — and closing the window stops the timer.
- **Run-queue reorder needed no work.** The request to add queue reorder and single-remove restated an existing capability: Core's `MoveInQueue` / `RemoveFromQueueAt`, the window's ↑ / ↓ / Remove buttons, and Core tests all shipped with the queue. Verified against the tree; nothing rebuilt.

## 2026-11-02 — Seamless updates: the installer closes and reopens the app (MuseDesktop R7D/R7D1 design, ported)

- **The direction: upgrading is hands-free after the user accepts it.** The accept step is untouched — the update window's Download → verify → Install, or the user running the installer themselves. Everything after that one decision needs no further interaction: no wizard in the in-app path, no "please close the app first", no manual relaunch. ArenaDesktop's installer used to do none of this; this entry ports the design MuseDesktop shipped as R7D (v1.8.4) and rebuilt as R7D1 (v1.8.5) after a field failure, with names adapted (ArenaDesktop.exe, arenadesktop://, Arena registry keys) and no Muse branding carried over.
- **The handshake, end to end.** The in-app Install now launches the verified installer with `/S` and does NOT exit the app itself (the old flow launched the wizard, then exited — replaced, because the installer's relaunch decision comes from detecting the RUNNING instance at install start). At the top of its main section — before any file is copied — the installer checks whether ArenaDesktop is running; if it is, it runs the INSTALLED `ArenaDesktop.exe --exit-for-update`. That second process reduces the flag to a new intent (Core: `LaunchIntentKind.ExitForUpdate`), writes it to the pending-intent file, knocks the wake event, and exits; the running instance applies it through the ordinary exit path (`ExitApp` — state saved, tray disposed). The installer then polls for the process to disappear (≈15 s), falls back to asking every ArenaDesktop process to close its main window (PowerShell `CloseMainWindow`, ≈10 s), then to `taskkill /F` (≈5 s), and proceeds with the install regardless.
- **Detection is process-based from day one — the mutex design is deliberately NOT ported.** MuseDesktop's first version detected the running app by opening its single-instance mutex (System plugin, OpenMutexW) and that check never once fired in the field: the close was silently never attempted. Its replacement asks PowerShell `Get-Process ArenaDesktop` and reads the answer from the exit code (0 = running, anything else = not running): no object names to match, no handles, no plugin call shapes. Every step of the close chain prints a `DetailPrint` line, so a future field failure leaves its story in the install details view instead of silence.
- **The exit intent is the ONE intent that never waits behind the app lock.** Core's routing (`LaunchIntentRouting.AppliesImmediately`) applies it at once, locked or not: exiting reveals nothing, navigates nowhere, and names no profile, and the lock re-engages at the next launch as after any exit. Every other intent keeps the S11 rule. It also never shows the window: the wake handler feeds `ApplyLaunchIntent` directly, so a tray-hidden instance exits without ever appearing. And a `--exit-for-update` launch that finds NO running instance exits quietly itself instead of starting the app the installer is about to replace.
- **Relaunch belongs to the finish page; silent mode is the one exception, and its reason is consent.** Interactively, the ONLY relaunch is the finish page's "Run ArenaDesktop" checkbox, which MUI fires as the wizard closes — the app starts as the installer goes away, and only when the box is ticked. When the app was running at install start, `AdFinishPageShow` pre-ticks the box (the app was open — bring it back); the user's untick always wins; when nothing was running, the box keeps its stock state. A `/S` run has no finish page and no checkbox, so a hidden last section relaunches the app when it was running AND the run is silent: in-app installs are that silent path, and the click on Install inside the app IS the consent.
- **The uninstaller runs the close chain too — a deliberate difference from MuseDesktop's script.** MuseDesktop's uninstaller does not close the app (its file removal simply leaves anything locked in place). ArenaDesktop's uninstaller runs the same chain first (DetailPrint prefix "Uninstall"): a running instance would otherwise lock the program folder, and — when the user answers Yes to deleting data — the WebView2 profile folders the app holds open. The chain is one shared macro (`AD_CLOSE_RUNNING`), so install and uninstall can never drift into different close behavior.
- **Deliberately not ported.** MuseDesktop's saved-password wipe (its R7F) is a Muse-specific repair for passwords its pre-v1.8.8 builds let the web view save, driven by an owner rule about that app; it is not update machinery and ArenaDesktop has no equivalent legacy state to repair. The rollback path (`ReinstallPreviousVersion`) is also untouched, exactly as in MuseDesktop: kept installers predate this feature, their handshake cannot be assumed, so rollback keeps its confirm → wizard → exit flow with no silent flag and no auto-relaunch.
- **Old builds facing the new installer.** A pre-port build tolerates the unknown flag (arguments are never fatal) and merely wakes its window, so the handshake politely does nothing and the fallbacks do the close — still automatic, still relaunched, just less gentle. Updating FROM v0.3.0 or older therefore works; the fully gentle path needs both sides at this version or later.
- **Windows runtime: Unverified**, like the rest of the app, until the on-machine pass runs: the process check's timing on a real machine, the pre-ticked box, the silent relaunch, and the uninstall close are all field checks now listed in RELEASE_CHECKLIST.md.

## 2026-11-02 — Modes pack (v0.3.0): route health, startup mode, favorite modes

- **Route health is reachability-only, by design.** Diagnostics' "Check mode routes" asks each registered mode route's server to answer (HEAD, GET only where HEAD is refused with 405) and classifies the outcome in Core (`RouteHealth`): 2xx/3xx and 401/403 mean the route exists, 404 means Arena moved it (the one verdict that asks for a registry update), everything else — network error, timeout, 5xx — is Unreachable. Response bodies are discarded unread (headers-only reads): the check never looks at page content, keeping the standing no-page-reading rule. The log records host + path and the verdict class only. Classification and formatting are Core-tested; the HTTP calls are the shell's.
- **The startup mode composes with the start page; it does not replace it.** The per-profile start page (S5 #47 — restore last page / Home / custom URL) names a PAGE and still wins wherever it does so. The new app-wide `StartupMode` string ("battle" default, "last", or "mode:<id>", resolved by `StartupModes.ResolveStartupMode`, unsalvageable values sanitize to "battle") only picks which mode page stands in for Battle when a launch would land on the Arena home page anyway — no crash restore, no custom fallback, never in safe mode. Default = Battle = exactly today's behavior.
- **Last-used mode is stored per profile.** `LastModeIdByProfile` sits next to `LastUrlByProfile` and follows its reasoning: Arena sessions are account-scoped, so one profile's last mode is never another's startup suggestion. It is session state, not a preference — reset-all-settings preserves it, while `StartupMode` and `FavoriteModeIds` reset with the other preferences.
- **Favorites are a short ordered list, sanitized like everything else.** At most three ids (`FavoriteModes`), unknown ids and duplicates dropped on load. They lead the tray's Arena modes submenu (starred, one separator) and the Jump List's modes category — where Battle and Leaderboard, the pair the list has always carried, still follow when they aren't favorites themselves. No favorites = both surfaces keep their exact previous order.
## 2026-11-02 — Battle Lab pack (v0.3.0): copy targets, library transfer, queue and journal tools

- **Copy targets are the three text modes, through the same callback.** The copy button's picker offers Battle, Direct Chat, and Side by Side (the modes with a prompt box worth pasting into). The Battle Lab → main window callback now carries the mode id (`Action<string>`), and the main window resolves it through `ArenaModes.TryGet` with Battle as the fallback — the same registry dispatch as every other surface, and Battle remains the default when nothing is picked. The copy itself is unchanged: fill blanks, clipboard, user pastes; nothing is injected.
- **The library export format carries a marker and a version.** Exports are `{ "format": "arenadesktop-battle-lab", "version": 1, "prompts": [...] }` with only the prompts inside — the queue and journal are this PC's run state and do not travel. A file whose marker or version doesn't match, or that won't parse, imports nothing and is reported as "not a Battle Lab library file", so a settings export or random JSON can never half-merge.
- **Import merges; it never replaces, and ids are always fresh.** An incoming prompt is skipped when one with the same name (case-insensitive) and the same body is already in the library; everything else is added under a NEW id minted by the library (the file's ids are not even reused as slugs), so an import can never collide with or silently overwrite an existing prompt.
- **One cap for merge operations.** The library cap (`BattleLabLibrary.MaxPrompts`, 200) is enforced by Duplicate and Import — the two operations that can grow the library in bulk or by accident — which stop at the cap and say so, rather than trimming anything already there.
- **The scoreboard tallies what is on screen.** The journal's tally is computed over the currently filtered entries, in Core (`BattleJournalTally`), and the Markdown journal export renders exactly that filtered set with its tally — filter first, and both the line and the file describe the same battles.

## 2026-11-02 — Battle Lab (v0.2.0): prompt library, run queue, results journal

- **A side pane, not a window (changed v0.8.0).** Through v0.7.0 Battle Lab was a modeless window, chosen so that copying a prompt could bring the main window forward while the Lab stayed open. The user asked for the two to be visible at once, so the Lab is now a split pane in the main window: the Arena page keeps column 0, the Lab takes column 2 behind a draggable splitter. Every entry point — the ⋯ menu, the tray, `--battle-lab`, `arenadesktop://battle-lab`, Ctrl+Shift+B — opens the same single pane. `BattleLabWindow` is deleted; `BattleLabView` is the control.
- **The pane reflows instead of being crushed.** The Lab was drawn for a 1220px window (272 + flexible + 356). Half a 1280px window would leave the editor around a hundred pixels, so `SplitWorkspace` picks one of three arrangements from the pane's width: three columns at ≥940px (the original shape), two columns with the journal stacked underneath at ≥600px, and one tabbed column below that. Thresholds and floors live in Core with tests, not as literals in the window. The reflow is driven through `PaneArrangementTracker`, so a drag-resize only rebuilds the grid when the arrangement actually changes.
- **Two panes need room, and the floor is explicit.** `SplitWorkspace` refuses to split below 706px of content width (360 page + 6 splitter + 340 pane). Below that the shell widens the window first; if that still is not enough, it says so in the status bar and stays single-pane rather than showing two unusable slivers. Dragging the splitter can never push the page under its floor — `ResolvePaneWidth` clamps, and a test sweeps the range.
- **The Lab's state survives closing.** The control is built once and kept in the window after the pane is closed, so reopening lands on the same prompt, filters and queue instead of starting over. The clipboard timer stops when the control leaves the tree.
- **Copy, never inject.** "Copy prompt & open Battle" fills the prompt's [blank] placeholders in a small dialog, puts the finished text on the clipboard, and navigates the main window to Battle through the ArenaModes registry. The user pastes. This keeps the standing rule intact: the app never injects script into arena.ai and never reads anything back from the page.
- **The journal is manual by design.** Results (A won / B won / Tie + note) are recorded by the user; nothing is scraped or detected. Journal entries snapshot the prompt name, so deleting a prompt never rewrites history.
- **One JSON store, Core-owned.** `BattleLabLibrary` / `BattleLabStore` in `ArenaDesktop.Core` hold all logic and persistence (`battle-lab.json` in the app data folder), following the repo's store patterns: atomic replace, a corrupt file preserved as a `.corrupt-…` copy with an empty library loaded, autosave on every change, and four editable seed prompts written only on first run (deleting them all is permanent — no re-seeding).
- **Queue completion is automatic but honest.** "Use next from queue" starts the head prompt; when a result is logged for that prompt while it is still at the head, it leaves the queue. Explicit Remove and Clear are always available, and nothing else is removed implicitly.

## 2026-10-27 — ArenaDesktop v0.1.0: a MuseDesktop-parity fork for arena.ai

- **Fork, don't reinvent.** ArenaDesktop starts from the MuseDesktop codebase (same author's MIT project) at its v1.0.0-era tree, renamed throughout. Reason: the parity target — tray, downloads manager, profiles, app lock, recovery, in-app updates with hash verification — is already built and covered there by a large Core test suite. A clean room rewrite would re-learn the same WebView2 lessons at full cost. The fork keeps the Core/shell split: all testable logic in `ArenaDesktop.Core` (plain .NET 10, no Windows APIs), the WPF app as a thin shell.
- **Stack deviation inherited: C# / WPF + Microsoft's WebView2 SDK instead of Rust.** The documented MuseDesktop reason stands: the first-party SDK is what exposes the exact features this shell needs (persistent user-data folder, new-window/navigation events, permission requests, download operations with progress + ETA). WebView2 SDK stays pinned at 1.0.4258.31; bumps are deliberate, with release notes checked.
- **Version restarts at 0.1.0.** ArenaDesktop is a new product; carrying MuseDesktop's version history would lie about its maturity. Its Windows runtime is Unverified until the release checklist runs on a real machine.
- **URL policy for Arena.** Home is `https://arena.ai/`. New-window in-app hosts: `arena.ai`, `lmarena.ai` (Arena's previous domain, still linked from older content), and the sign-in providers Arena uses — `accounts.google.com`, `appleid.apple.com`, `login.microsoftonline.com`. Microphone and notification permissions auto-grant only to `https://arena.ai` origins; everything else is denied rather than silently granted. Full URLs are never logged (host + path only).
- **Arena modes are one registry.** `ArenaModes` in Core defines Battle, Direct Chat, Side by Side, Leaderboard, Agent, Image, Code, Video, and Web Search once; the window menu, the tray, the Jump List, Ctrl+1…Ctrl+9, the CLI flags, and `arenadesktop://` links all dispatch through it. Addresses verified against the live site on 2026-10-27: Battle is the home page; Direct Chat is `/text/direct` and Side by Side is `/text/side-by-side` (models picked at the top of those pages); Leaderboard is `/leaderboard`; Agent, Image, Code, Video, and Web Search are top-level pages. The app never injects script into arena.ai.
- **Global hotkey is Ctrl+Alt+A**, not MuseDesktop's Ctrl+Alt+M, so both apps can run side by side without fighting over the key. Registration id changed to match.
- **No winget.** The maintainer has no code-signing certificate; distribution is GitHub Releases only and binaries ship unsigned, stated honestly. The winget packaging folder from the fork base was removed.
- **Release shape.** x64 and ARM64 at v0.1.0 (the architectures the fork base's CI builds and verifies), with the fork base's asset naming, which the in-app updater pins in code and tests: `ArenaDesktop-Setup-v<version>-<arch>.exe`, `ArenaDesktop-v<version>-windows-<arch>.zip`, plus `SHA256SUMS.txt` — the sums file is a working part of the updater (it refuses a release without one), not decoration. x86 and MSI are not shipped in this version and are named as gaps in the release notes, not silently skipped.
- **Icons/assets.** The fork base's icon artwork is reused for v0.1.0 (renamed); a distinct ArenaDesktop icon is a capture/design task, not a blocker.

## 2026-11-23 — The command palette, and the layout cycle's home (v0.10.0)

- **The palette is a second door, not a second implementation.** `CommandPalette` in Core is data (37 commands at v0.10.0, 50 since v0.11.0) plus one search rule; the shell's `ExecutePaletteCommand` maps every id onto a handler a menu item or a key handler already called. Nothing in the palette reaches the Arena page, and no command exists only there. The shell runs the chosen id only after the dialog has closed, so a command that opens a window can never open it while the palette is still modal. Mode commands are generated from `ArenaModes.All` (`mode:<id>`), so Ctrl+1…Ctrl+9, the ⋯ menu, the tray and the palette cannot drift apart.
- **Search is prefix-per-term, deliberately not fuzzy.** Every whitespace-separated term must prefix some word of the title, group or keywords — identical to Settings, Help and the shortcut sheet. Fuzzy matching would make four search boxes answer differently and would rank a typo above the command the user asked for. A blank query lists everything, in fixed groups; the palette is also how people discover commands, so an empty box is not an empty window.
- **Ctrl+K is an in-app key, outside the remappable three.** The page never sees it (no injection, no page reading), it is not registered as a global hotkey, and it cannot be remapped: like Ctrl+Shift+B and Ctrl+Shift+P it joins the fixed catalog entry, which is what makes the shortcut sheet and the palette honest about it. Settings, Downloads and Home remain the only remappable bindings.
- **The layout cycle got its key from the palette's arrival.** `ShellLayoutCycle` had no caller since 2026-11-02 because the parity target puts its cycle inside a command palette. With one here, the cycle has three surfaces (Ctrl+Shift+K, the ⋯ Layout submenu, the palette) and still one rule, `ShellLayoutCycle.Next`.
- **The prompt pad's draft is a draft, not a document.** The box keeps its unsent text across close (v0.10.0), stored trimmed in `prompt-pad.json`, cleared the moment the prompt is copied. "Forget all" still only forgets the remembered prompts; the draft is not one of them. The pad still loses nothing silently: what it restores is exactly what was on screen.
- **Palette cadence: deliberately quiet.** No recency ranking, no usage history, no per-command arguments. Anything that would need to remember what the user ran is a settings surface and a privacy question, not a launcher.
- **Windows runtime: Unverified**, like the rest of the app, until the on-machine pass in RELEASE_CHECKLIST.md runs.

## 2026-11-23 — The pad can hand a prompt to the Lab (v0.12.0)

- **The pad writes the library, but never its file.** `PadHandoff.Keep(library, text)` is Core, working on a `BattleLabLibrary` the *shell* supplies. That is deliberate: `battle-lab.json` has exactly one in-memory owner at a time — the Lab pane once it has been built — so the main window routes the write through `_battleLab.Library` when the pane exists and opens the store itself only when it does not. Two copies of the same JSON writing over each other is the bug this rule exists to prevent, and the routing is pinned by a test.
- **Category "Prompt pad" instead of "General".** A handoff should be findable later as a group — "what did I keep from the pad?" is a reasonable question — and a prompt the user typed into the Lab by hand should not be mixed in with it.
- **Duplicates are refused by text, not by name.** The comparison is the body, surrounding whitespace ignored, against the entire library. That is the same rule the import path already uses, and it means keeping the same prompt twice from the pad is a no-op with an explanation rather than a second identical row. The library's 200-prompt cap is respected here too; before this, only import and duplicate checked it.
- **Keeping is not copying.** The box keeps its text and the draft is not cleared: the prompt is now in two places on purpose, and the user may still want to copy it and open a page. Copying still clears the draft (that text is in the remembered list by then).
- **The prompt text never reaches the log.** The outcome (`Kept`, `AlreadyThere`, `Empty`, `LibraryFull`) is logged; the text is not, on the same principle as page content — the log is for the app's behaviour, not the user's words.

## 2026-11-23 — Errors report themselves; Settings survives a bad panel (v0.13.0)

- **The crash box names the exception and the frame.** The v0.12.0 report was a screenshot of a dialog that said "details were written to the log" — true, and useless without knowing what to look for in a 1 MB file. `CrashReport` (Core) turns an exception into type, cleaned message, the first stack frame that is *not* the framework's (the app's own code, the only part a fix can land in), and the innermost cause, plus a bounded log tail. Pure text, no windows: that is why it can be tested at all.
- **The report is bounded and redacted.** 25 log lines, 4,000 characters, cut from the end; then `RedactionAudit.Redact` — the same pass the support bundle uses — so a query string, an address or a token in the log cannot ride out in a clipboard entry. A crash report leaves the machine only because the user pastes it somewhere, but "only because" is not a reason to include more than the bundle would.
- **The dialog offers the two actions that matter**: Copy details, and open the folder the log is in. No "send report", no upload, no telemetry — the privacy promise does not get a crash-shaped exception.
- **A crash handler may not crash.** `CrashPresenter` tries the window, falls back to the old message box with the summary, and swallows its own failures after logging them. `CrashWindow` is deliberately dependency-free — window-local styles only — because it may be built while the rest of the app is in a state nobody designed for.
- **Settings is guarded per step, not per attempt.** Wrapping the whole load in one try/catch would have left a half-filled window and a banner claiming more than it knew. Each load-time step that touches the disk, the registry or the page is wrapped individually (`Guard("the profile list", …)`): the failing ones are named in a banner and in the log with their step name, and the rest of the window is genuinely working. The banner sits above the search box so a search cannot hide it.
- **The window that fails to construct says so.** `MainWindow.OpenSettings` catches a failing `new SettingsWindow(…)` and reports "Settings could not open." with the exception summary, rather than letting the dispatcher handler turn it into an anonymous error with no window name in it. The same for the main window at startup.
- **Windows runtime: Unverified, and this release is the reason the label matters.** The dialog, the guard and the fallback are all shell behaviour; CI compiles them and pins their wiring, but nobody has yet clicked "Copy details" on a real machine. The v0.13.0 checklist entry is the first thing to run.

## 2026-11-23 — The app inspects itself; the palette takes arguments (v0.14.0)

- **A health check, not a self-repair wizard.** `DataHealth` reads each store the way its own loader would and reports Ok / Missing / Unreadable with a reason — never the file's content, because the reason is what a report needs and the content is the user's. Repair is deliberately two steps and in that order: `CorruptFile.Preserve` first, `File.Delete` second. If the copy fails, the original stays. The button's promise is therefore "nothing is lost", which is the only promise a repair button should make.
- **The crash ledger records endings, not events.** WPF only shows a dialog for the dispatcher's exceptions, so a background-thread crash used to leave nothing but a log line. Two more handlers record it now — and `OnExit` clears the marker, which is what makes "the last run ended in an error" a fact rather than a guess. A process that is killed never runs `OnExit`, and that is exactly the case the next launch should mention.
- **Three in ten minutes is a loop.** A threshold and a window, kept in Core and tested, because the alternative — asking "is this a loop?" at runtime — is a guess. When it trips, the dialog offers `--safe-mode`, which already exists and already solves the class of problem (a customisation that breaks startup).
- **Palette arguments are verbs, and refusals are searches.** `zoom 125` / `find cables` / `profile Work` / `mode side`; anything else is what it always was. A malformed argument deliberately does *not* clamp or guess — `zoom 900` searches instead of silently becoming 200%, because the palette's job is to do what was asked, not something adjacent. The argument is never logged; only the verb.
- **`[tone=neutral]` is a default, not new syntax for the page.** The blank's name stays `tone`, the user's value still wins, and a defaulted blank that nobody fills is not reported as unfinished — it *is* finished, by what the prompt's author wrote. Plain `[topic]` is untouched, so every existing prompt behaves identically.
- **ARM64 is built, never shipped.** The v0.7.0 decision to drop ARM64 shipping stands; what changed is that the publish is now exercised on every PR, because a target nobody builds is a target that rots. The guard test that used to forbid the word arm64 now forbids it everywhere except the CI job, and forbids any arm64 *asset* anywhere.
- **The records stay honest.** The field-pass export carries a `schemaVersion` and the same sentence the markdown does; the leaderboard says the results were entered by hand; the verification script writes "Not recorded" when nobody was there to look.
